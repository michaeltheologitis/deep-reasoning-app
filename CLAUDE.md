# deep-reasoning

A minimal chat for `deep_reasoner`, in one browser tab: chats on the left, the conversation on the right, and each run's sub-agents as a tree that clicks open and shut, in the look of Claude Code.

Read `../coding-skills/GUIDE.md` and follow it; in the main session a hook has already printed it.
This project's Notion page (todos, changelog, notes): https://app.notion.com/p/40362fb222378153b3a4edba29ea4329. The brief under its Notes is the whole context for the current work.

## Goals and non-goals

- The UI is agreed: the clickable prototype of PR #73. v1 built it for real, in five PRs: (1) the app shell; (2) the Library in `library.sqlite`; (3) runs: `deep_reasoner` in a subprocess, steps streamed live, Stop ends the tree, costs per call; (4) chats saved in `chats.sqlite`; (5) the UI wired to real data.
- No sandboxing or safety layers, and nothing from the old app's OpenHands or ACP stack.
- `deep_reasoner` is never changed for the app. How each part works is in its module's docstrings; this file keeps the decisions and invariants.

### The page and the server

- The page reads chats and runs from the API; `web/fold.js` folds a run's events into the tree, the same for a saved turn and a live one. A live run streams over SSE from `?after=` the last seq the page has, so a reload catches up without gaps or repeats.
- Tabs keep in step without a push channel: coming back to a tab reads the chats, the Library and settings again (and the model lists once the providers changed); the theme follows `localStorage`'s `storage` event. A tab's one-run-at-a-time lock holds only for runs it started (its own kept in `sessionStorage` across a reload, and followed first after it): it follows its own run and another tab's in the chat on screen, two streams at most, and sends past the latter; "+ New chat" reuses only the empty chat on screen or one the tab made. At phone width a side panel, or the open drawer, covers the page, and what is behind it is `inert`.
- Answers and pages are model output: Markdown only where marked finds some, else shown as written; raw HTML shows as text, an image is a link, never fetched, links open in a new tab, and DOMPurify keeps only what marked makes and web, mail or relative links (`web/tree.js`).
- The server listens on 127.0.0.1 only, and refuses requests naming another host or sent from another site's page (`Origin`). Its pages carry a Content-Security-Policy, so they load and send nothing but to the app, whatever an answer holds.

### The app file

- One SQLite file (default `~/.deep-reasoning/library.sqlite`, `--library PATH`) holds the Library (every namespace, decomposition and custom tool's source, and the run settings, each as the engine's own YAML), the chats with their runs' events and pages, and the app's settings; `library.py` lays it out. Latest only: copying the file is the snapshot of all of it but the keys and the runs' working folders; `reset` deletes it to start afresh. It holds no model or client: each chat picks its model.
- Each file's run and scratch folders are in a data folder of its own in the app's home, named from its real path, so a copy never shares them and a moved file starts afresh, deleting nothing.
- Schema version 4 (`PRAGMA user_version`); a version 1–3 file opens and gains the tables it lacks, keeping what it holds; any other file is refused untouched. Only a new file is seeded (the namespaces, worked examples and root suffix below): an older Library isn't changed.
- A file that can't be written (read only, full, busy) answers 400 in plain words; any other SQLite error is a bug and stays a 500.

### Trust boundary: a shared file

- Everything read from the file is checked as the app could have written it (Library rows as the engine reads them, within 1,000,000 characters, names in printable ASCII and not root's, templates as a save checks them; custom servers, settings, chats, runs, events, pages), and what fails is left out with a warning, so it reads as unset; the panel lists each Library row left out, to fix or delete. The page and the `history` tool read a run's record as untrusted too.
- Deleted rows are wiped (`secure_delete`) and the file's own triggers and views never run, so a copy carries nothing deleted.
- The engine's templates render sandboxed in the app's processes, so a shared file's worked example, prompt or suffix reaches no Python internals.

### Tools build in every run

- The engine builds every tool a config declares, whichever namespace the run enters, so `engine_config()` declares only those some namespace grants: a granted tool's code runs at the start of every run of every chat, and one that fails to build stops every chat until no namespace grants it (the failed run says which, where and how to take it out). A tool no namespace grants never runs, but for a build check.
- So every write that newly grants a custom tool (the panel, the librarian, an import) builds it first, in a process of its own from an empty folder, and is refused if it doesn't build: keyless for the panel and an import, as a run would for the librarian.

### The Library panel and import

- The panel adds, edits and deletes namespaces and decompositions, root's included (the root lock is the librarian's); deletes a tool no namespace grants and a run setting the engine doesn't know or that is left out. Each namespace change is checked by the engine over the whole Library in one transaction.
- An edit or delete carries the YAML it was opened on and is refused with 409 if that changed since; the panel then shows what is stored, keeping the draft. The panel and the namespace menu read the Library again when opened or the window comes back. A chat whose namespace was deleted is refused on its next run until it picks another.
- Decompositions are checked as worked examples by the rules the engine's own examples keep (`turn_problems`, and its twin `web/turns.js`, held to its words by `tests/turn_cases.json`), the code not run: problems mark one ✗ but never refuse it, so a draft is stored. Saving refuses one over 1,000,000 characters, oddly named, or with a template the engine couldn't render or that reaches Python internals (checked, never rendered). A namespace is refused for a backbone, suffix or var the engine can't take there or below.
- After each namespace's own `system_suffix`, a run tells its agents which namespace they are in (not root's), where their Python runs when their REPL isn't the one above (root's: the local one), and, when it sets a `spawn` list, where they can hand work (`run_lines`); the line isn't stored, the library tool refuses a suffix holding one, and the panel shows it as added at run time.
- `deep-reasoning import` writes, in one transaction, what the Library doesn't hold and root's fields over root's own, and says what it changed, left out and what that changes in the app. It refuses, changing nothing, a file that isn't a config, the app's own namespaces or one under them, a tool named as a built-in, what the panel would refuse, an `entry_namespace` naming no namespace, a template variable a kept worked example reads, and a key; it reads only files in the config's folder (`--within` widens it).

### Keys

- Keys live in `.env` in the app's home, readable only by the user (0600), and nowhere else: never in the Library, chats, run folders, events, logs or responses (a provider's key that a cell prints, the run's or any set in the shell, is withheld from its events, unless shorter than 8 characters, as no secret; other secrets a cell reads from the shell travel with the file); the page gets only a status per provider (`set`, `shell`, `none`). A key saved there wins over the shell's.
- A custom server's key, saved or from the shell, goes only to the address it was saved for, recorded beside it in `.env`; a server of that name at another address, as a shared file may hold, has no key until one is typed for it.
- The known vendors, their addresses and the few current models the model menu features for each (strongest first, checked against each vendor's models page on the date its comment names) are `VENDORS` in `settings.py`. A call is priced by the server's own figure, else by genai-prices only for the vendor at the client's `base_url`.
- A run's config is `engine_config()` with the chat's model and its provider's `base_url` and `api_key_env` put in, and the key reaches the worker in its environment only. Never `ANTHROPIC_API_KEY`: Anthropic's key is `DEEP_REASONING_ANTHROPIC_KEY`, and the worker never gets `ANTHROPIC_API_KEY`.

### Chats, runs and folders

- A chat (`chats.py`) holds its title and what its next message runs on and in: namespace, model with its provider, working folder. Its turns are its runs (`runs.py`), each event saved as it happens, one commit each, in WAL mode with `synchronous=NORMAL` so no event waits on an fsync; the `-wal` and `-shm` files fold back when a run ends, so a copy made with the app stopped is whole.
- A follow-up's run gets the chat's earlier messages and answers as the conversation's own turns, each answer as the cell that gave it, marked as folded, so root hands questions about its work to the historian.
- A run the app stopped under is ended failed at the next start; an event the file refuses ends its run failed, and the chat takes its next message. Deleting a chat deletes its runs, pages and scratch folder, and ends its run going. An older version's files in the app's home are left unread, until `reset` of the default file deletes them.
- A chat's working folder is the worker's cwd: the one the user chose, never deleted, or its scratch folder, deleted with the chat; a run in a folder that is gone is refused. The worker starts with `python -P` and puts the folder last on `sys.path`, so the user's modules never shadow an installed one. The run's own files stay in `runs/<run>/` in the data folder.

### The app's tools

- `app_tools.py` holds the agent's own tools, loaded through the engine's `factory_from`, so the engine never changes. Their blocks are added in code, never stored, and their names are reserved. Each opens the file as it is, never making a moved or deleted one afresh.
- `history` (read-only) returns the chat's earlier runs as plain data, through a Python twin of `fold.js` (both end what a run left going as stopped with a run that was stopped, else cut off). A fresh Library grants it, with `page`, only in the `historian` namespace it seeds (`spawn: []`); root holds each historian example's first two turns, the question and its hand-off with the message as written, which every namespace inherits but the historian, whose own take their place.
- A namespace that can't make a worked example's hand-off (its `spawn` list leaves the target out, or the target is gone) is shown it doing what it can instead, at run time only; the panel says so under the namespace's Hand-offs.
- `page` shows the user a page the app draws from plain data, never HTML (text, tables, and steps or sub-agents copied from the record), keys withheld, saved in the `pages` table and linked from the chat.
- `library` is granted only in the `librarian` namespace a fresh Library seeds, which nothing inherits, with `spawn: [historian]`: a default the user may widen, not a lock, so it never delegates to itself. Root holds two hand-offs to it, nearer the task than the historian's, as root follows those more reliably. Root's seeded `system_suffix` says what app its agents are in, names no librarian, and carries the guidance on numbers and fan-outs as a suffix, which measured better per token than a worked example.
- `library` reads from any namespace. It writes decompositions, namespaces' own fields (`system_suffix`, `vars`, `tools`, `spawn`) and custom tools, with the panel's checks, only in a run whose chat's namespace grants it through its chain: a sub-agent spawned into `librarian` from another chat can't, and a librarian chat's agent may pass it to a sub-agent where its `spawn` allows. A tool it writes or newly grants is built first, only in a chat on the `local` REPL, as the build runs the agent's code unsandboxed.
- Its locks, checked before any build and again under the write lock: it never writes root, its YAML or its decompositions; never sets or changes a namespace's `repl` or `reasoner` (`reasoner: claude_code` would bill Michael's subscription), or which namespaces grant the app's own tools (the user's, in the panel); adds no namespace under one whose chain grants `library` or runs Claude Code; grants no tool running Claude Code afresh, nor names a tool's factory as one of the engine's; writes no tool under a reserved name, over one root grants or over one the engine builds from its block alone; has no method for the system prompt, the run settings or deleting; and writes only plain text or data, never a key, over 1,000,000 characters, or a text a brief list cut. They are in `app_tools.py`, as the panel still edits all of it; they guard the tool, not the file, which a cell can open itself. Every refusal is a `LibraryError` in plain words.
- Each change is logged as `library.change` with its before and after, a step of the agent that made it; a Stop never falls between a write and its log. The chat shows each as a step and a line under the answer, opening onto its before and after as untrusted text; the panel and the namespace menu read the Library afresh. A change applies from the next message; undoing one is asking the agent to write the before back. The design is the sub-page under the Notion page's Notes.

## Checks

- `uv sync`, then `uv run deep-reasoning` serves the app at http://127.0.0.1:8000 and opens a tab (`--port` to change the port, `--no-browser` to skip the tab). `uv run deep-reasoning import CONFIG.yaml` reads an engine config into the Library. Serving, `import` and `reset` each take `fcntl.flock` on `<the file's real path>.lock` (a file of its own, as SQLite's locks are on the Library's) before they open the file, refuse while another holds it, and never delete it; where flock isn't supported they warn and go on. A `--library` in a missing folder is refused. `uv run deep-reasoning reset` deletes the app file's side files, then the file, its data folder and, for the default file only, an older version's leftovers in the app's home, after listing them and asking (`--yes` doesn't ask). It refuses, deleting nothing, anything but a file it can read as a version 1–4 Library, and writes nothing before the user types `delete`; it keeps `.env`, every folder a chat or the settings chose, and a folder holding one. The UI is static files in `src/deep_reasoning/web/`, no build step, served at `/`; marked, DOMPurify and js-yaml are cdnjs's pinned files copied into `web/vendor/`, so the page loads nothing from elsewhere.
- `uv run pytest` (no network: the model is a fake on 127.0.0.1); `node --test tests/*.test.mjs` (the fold, the tree, the model menu and the turn check, no dependencies); `uv run ruff check && uv run ruff format --check`; `node --input-type=module --check < FILE` for each of `src/deep_reasoning/web/app.js`, `fold.js`, `tree.js`, `models.js`, `page.js`, `library.js`, `settings.js` and `turns.js` (as modules: a plain `node --check app.js` misses errors such as a name declared twice, which stop the page loading).
- `uv run pytest -m live -s` runs the gpt-6-luna live test, a paid call, and logs what it spent; it needs `OPENAI_API_KEY` (in a cloud session `OPENAI_API_KEY=placeholder`: the network proxy adds the real one).
- Check each UI change in a real browser against `uv run deep-reasoning --no-browser` (Playwright is preinstalled in cloud sessions): a new chat, a live run with its tree opened, a follow-up, a reload mid-run, Stop, rename, delete, a restart, both themes, phone width, no console errors.
- To drive the UI without a paid model: serve `tests/fake_model.py`'s `FakeOpenAI` from a process of its own on a scripted plan (`scripts/record_runs.py` has fan-outs, nested delegation and a run to stop), run `HOME=<tmp> uv run deep-reasoning --no-browser --library <tmp>/lib.sqlite`, add the fake in settings as a custom server (its `base_url`, any key), and pick one of its models under the input (`library_on` in `tests/conftest.py` does the same through `settings.py`). `HOME` keeps its keys, runs and scratch folders out of your own `~/.deep-reasoning`.
- The fold's fixtures in `tests/runs/` are real runs against the fake model, recorded from the app file, never typed: `uv run python scripts/record_runs.py`. Record them again when the worker's events change.

## Conventions

- A PR that adds or changes what a user can do updates README.md's list of what the app supports in the same PR.
- No paid model calls except the gpt-6-luna live tests, and the Claude Code on Sonnet live test through Michael's subscription token. Never set `ANTHROPIC_API_KEY`.
- Tests import copies of `deep_reasoner`'s example configs in `tests/configs/` (0.3.0's `docs/configs`, same layout); refresh them from the pinned tag, never edit them.
- Kill only the processes you started: never `pkill -f` or `pgrep -f`. `uv run` puts a Python child under its own process, so stop both (or run `.venv/bin/python` directly), and check with `ps` that nothing you started is left before you report.
- `deep_reasoner`'s repository is read-only for us: no PRs, issues or comments there. The app depends on it from GitHub, pinned to a tag in `pyproject.toml`.
- The previous app is in history at `a80bb2e` (`git show a80bb2e:<path>`), and its design docs are on the `design-docs` branch. In a shallow clone, run `git fetch --unshallow` or `git fetch origin design-docs` first.
