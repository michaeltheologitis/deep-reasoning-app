# deep-reasoning

A minimal chat for `deep_reasoner`, in one browser tab: chats on the left, the conversation on the right, and each run's sub-agents as a tree that clicks open and shut, in the look of Claude Code.

Read `../coding-skills/GUIDE.md` and follow it; in the main session a hook has already printed it.
This project's Notion page (todos, changelog, notes): https://app.notion.com/p/40362fb222378153b3a4edba29ea4329. The brief under its Notes is the whole context for the current work.

## Goals and non-goals

- The UI is agreed: the clickable prototype of PR #73. v1 built it for real, in five PRs: (1) the app shell; (2) the Library in `library.sqlite`; (3) runs: `deep_reasoner` in a subprocess, steps streamed live, Stop ends the tree, costs per call; (4) chats saved in `chats.sqlite`; (5) the UI wired to real data.
- The page reads chats and runs from the API. `src/deep_reasoning/web/fold.js` folds a run's events into the tree the chat draws, the same for a saved turn and a live one, walking a node's ancestors once each, as a shared file may name a node its own ancestor; a `library.change` is a step of the agent that made it, after its cell, and is listed on the turn (`turn.changes`, each with the tasks above it) for the lines under the answer, as a `page.open` is (`turn.pages`); a live run streams over SSE from `?after=` the last seq the page has, so a reload catches up without gaps or repeats, and reopens the nodes the tab had open (sessionStorage, by run and path, `nodesOf`). A sub-agent's own calls (usage `own`) on another model than the run's name it on its row; a run whose only chat calls never finished (`unfinished_calls` on its `turn.end`, counted by the worker's `counting_calls`) costs unknown, not its total's 0. An answer, and a page's text, is Markdown only where marked finds some (`markdownHtml` in `tree.js`), else shown as written; raw HTML shows as text, after an inline `<code>` too, `_` never emphasises nor `*` touching a letter or digit outside it (but of a script written without spaces: Han, kana, Hangul, Thai and the like), only `~~` strikes, an image is a link, never fetched, links open in a new tab, and DOMPurify keeps only the tags and attributes marked makes and web, mail or relative links (`SANITIZE`).
- The server listens on 127.0.0.1 only, and refuses requests naming another host or sent from another site's page (their `Origin`). Its pages carry a Content-Security-Policy (`CONTENT_SECURITY_POLICY`), so they load and send nothing but to the app, whatever an answer holds.
- The Library file is the app file: one SQLite file (default `~/.deep-reasoning/library.sqlite`, `--library PATH` for another) holding the Library (every namespace, decomposition and custom tool's Python source, and the run settings, each as the engine's own YAML), the chats with their runs' events and pages, and the app's settings. Latest only: sharing or copying the file is the snapshot of all of it, but not the keys or the runs' working folders, and deleting it (`deep-reasoning reset`, with its data folder) starts afresh. A shared file is a trust boundary: what is read from it is checked (each Library row as the engine's models read it, within 1,000,000 characters, no run setting the Library never holds (`NOT_RUN_SETTINGS`) or `entry_namespace` the engine can't enter, a namespace under one left out going too and a grant of a tool left out ignored; the panel lists each ✗ with why, to fix or delete; each custom server as `add_server` checks one, and not under another provider's name or key variable; each setting's shape; each chat's id and folder; each run's id, as it names a folder; each event row, which must load to an object with its seq (from 1), a time and a kind and no number past ±2**53, and a run's turn.start with its prompt; each page's row and blocks, walked, not recursed, as `pages.py` reads them), and what fails is left out with a warning, so it reads as unset. Deleted rows are wiped (`secure_delete`), and the file's own triggers and views never run (`setconfig`), so a copy carries nothing deleted. A Library file that can't be written (read only, full, busy) answers 400 in plain words; any other SQLite error is a bug and stays a 500. Each file's run folders and scratch folders are in its data folder, `files/<first 16 hex of the sha256 of its real path>/` in the app's home (`folders.data_folder`), so a copy never shares them with the original and a moved file starts afresh, deleting nothing. Schema version 4 (`PRAGMA user_version`); a version-1 file (the Library alone), version-2 file (no runs) or version-3 file (no pages) opens and gains the tables it lacks, keeping what it holds; any other file is refused untouched. `src/deep_reasoning/library.py` is the Library's store and lays the whole file out; `engine_config()` turns it into the config dict `V2Config` reads at run start, with only the tools some namespace grants, the app's own included, and, after the own `system_suffix` of each namespace that sets a `spawn` list, a line saying where its agents can hand work, worded around the system prompt's fan-out (`spawn_lines`; the run's only, shown in the panel as added at run time). The engine builds every tool a config declares, whichever namespace the run enters (only which agents see a tool is per namespace), so once any namespace grants a tool, its module and factory run at the start of every run of every chat, and one that fails to build stops every chat until no namespace grants it (the failure of a run whose tools don't build at its start, worded by `build_failure` in `worker.py`, names the tool, the namespaces that grant it (`granted_in`) and how to take it out; the panel lists every tool, granted or not, and a custom tool's description as far as its source says, read with `ast`, never run: `source_description`, its `Func`'s description or else the docstring of what it wraps); a tool no namespace grants never runs, but for the library tool's build check. `deep-reasoning import` (`importing.py`) writes only what the Library doesn't hold, root's fields over root's own, says what it changed and left out (a key `V2Config` doesn't define among it), and what that changes in the app (`import_report`, built in its transaction from the engine's registry before and after), and refuses, changing nothing, a file with no key it defines, the app's own namespaces or one under them, a tool named as a built-in but for that built-in's own settings, what the panel's save refuses (`check_written` per namespace, as the panel calls it), and a key (`every_key`). The custom tools it newly grants, stored or imported, are built keyless (`keyless_environment`, `refuse_unbuilt_keyless`) after the engine's check, in its one write transaction, which the app's lock keeps every other writer out of. It holds no model or client: each chat picks its model, and an older file's are left unread. `deep_reasoner` is never changed for it. The panel adds, edits and deletes namespaces and decompositions, root's included (the root lock is the librarian's) (the API's `/api/namespaces`, `/api/decompositions`), each namespace change checked by the engine's `NamespaceConfig` and `registry.check` over the whole Library in one transaction, the custom tools it newly grants built keyless first (`built_grants`, shared with the librarian); deletes a tool no namespace grants (`/api/tools`) and a run setting `V2Config` doesn't know or that is left out (`/api/run-settings`); an edit or delete carries the YAML it was opened on (`was`) and is refused with 409 (`ChangedMeanwhile`) if it changed since, or went (worded as a delete), and the panel then shows what is stored, keeping the draft, or, when the Library read again no longer holds it, says the refusal where its tab says a delete; each namespace and tool row carries its `refusal`, from the server (`namespace_refusal`, `tool_refusal`, which the deletes raise: a granted tool, a namespace with children or in another's own `spawn`), which the panel says before the confirm; it reads the Library again when opened or the window comes back, as the namespace menu under the message box does (`GET /api/namespaces`). A chat whose namespace was deleted is refused on its next run until it picks another. Each decomposition's turns are checked as a worked example (`turn_problems`, by the rules the engine's own docs/configs namespace examples keep: the task first, after any system turns; turns alternating; each assistant turn a `<think>` and one `<repl>`, checked as the one the engine runs (the last; blank is none); after a cell that didn't call `FinalAnswer`, its `<observation>`; `FinalAnswer` last), its code not run; problems never refuse one, so a draft is stored, but saving one (POST, PUT, `write_decomposition`) is refused past 1,000,000 characters, named with outer spaces or invisible characters, or with a turn holding `{{` or `{%` whose template doesn't parse and compile, names more than the engine fills in, includes another template (`include`, `extends`, `import`, `from`) or reads a Python internal by a name it gives (`template_problems`: `FILLED_IN` and `prompt_template_variables`, Jinja's globals such as `range` not counted; an attribute starting with `_` or named in the sandbox's `UNSAFE_*` sets or `mro`, or a constant key starting with `_`; checked, never rendered, so it runs nothing and attributes such as `vars.x.value` go unchecked; a stored one that fails is marked ✗ with why). The engine's templates render sandboxed in the app's processes (`sandbox_templates`, which the worker calls first: Jinja's `SandboxedEnvironment`, with no templates to include), so a shared file's worked example, system prompt or suffix reaches no Python internals: a worked example that tries fails its run, naming it, and a prompt or suffix is shown as written. A namespace is refused with a backbone the engine doesn't build there or below (`check_backbones`; an import checks every namespace), a `system_suffix` that `template_problem` refuses (`suffix_problem`, as the panel, the librarian and an import save it), or a var that isn't a Python name, starts with `_`, is a keyword or a built-in, or that a tool it or one under it sees takes the place of (the engine binds tools over vars). Turn problems: the Decompositions tab marks each ✓ or ✗ with them, `panel()`, `library.show()`, the POST and `write_decomposition` return them, and the add form warns with them as you type through `web/turns.js`, its twin, held to its words by `tests/turn_cases.json`.
- Keys live in `.env` in the app's home, readable only by the user (0600), and nowhere else: never in the Library, chats, run folders, events, logs or responses (a provider's key that a cell prints, the run's own or any provider's key variable set in the shell, is withheld from its events as `[key withheld]`, unless shorter than 8 characters, as no secret; other secrets a cell reads from the shell travel with the file); the page gets only a status per provider (`set`, `shell`, `none`). A key saved there wins over the shell's. A custom server's key, saved or from the shell, goes only to the address it was saved for, recorded beside it in `.env` (`DEEP_REASONING_<NAME>_URL`). Typing a key for a server records its address; with no key typed, adding a server records it only while no other address holds the name, and changing a server's URL moves it only when it was that server's. A server of that name at another address, as a shared file may hold, has no key ("none"), even after Save, until a key is typed for it, which rebinds the name; removing it leaves the user's key alone. The known vendors, their addresses and the few current models the model menu features for each (strongest first, checked against each vendor's models page on the date its comment names; typing searches the chat models of the vendor's whole `GET /models`, `is_chat_model`) are `VENDORS` in `src/deep_reasoning/settings.py`; a call is priced by the server's own `usage.cost`, else by genai-prices for the vendor at the client's `base_url` only (`cost_of` in `worker.py`), so a vendor's model name elsewhere is unpriced; custom servers (any OpenAI-compatible URL), the model picked last and the default folder are in the app file's `app_settings` table (key, JSON), apart from the Library's `settings` table, which is the run settings. A run's config is `engine_config()` with the chat's model and its provider's `base_url` and `api_key_env` put in, and the key reaches the worker in its environment only. Never `ANTHROPIC_API_KEY`: Anthropic's key is `DEEP_REASONING_ANTHROPIC_KEY`, and the worker never gets `ANTHROPIC_API_KEY`.
- Chats are in the app file's `chats` table: each chat's id, title, when it was made, and its namespace, model (with the provider that serves it) and working folder, from its next message. `src/deep_reasoning/chats.py` is the store. The API lists the chat used last first, each with its `last_run`. The page reads the list and the open chat again when its window comes back, and follows a run another tab started there; a 404 for a chat means it was deleted elsewhere; "+ New chat" goes to an empty chat if there is one. A chat's turns are its runs, in the same file (`src/deep_reasoning/runs.py`): the `runs` table names each run's chat, and `events` holds each event as the JSON the page folds, saved as it happens, one commit each on the event loop, in WAL mode with `synchronous=NORMAL` so no event waits on an fsync. A follow-up's run gets the chat's earlier messages and answers as user and assistant turns, after one system note, an answer as the `<repl>` cell calling `FinalAnswer` that gave it, under a `# folded:` comment saying the work behind it isn't shown, so root hands even vague questions about it ("did any of them have trouble?") to the historian, the engine's own way (`dr repl exec` for Claude Code). The `-wal` and `-shm` files beside the file exist while a run is going and fold back when it ends, so a copy made with the app stopped is whole. Deleting a chat deletes its runs' events and its pages, and the next start deletes those of a chat deleted before them; a run the app stopped under, with no `turn.end`, is ended failed when the app next starts, and one it can't end (unreadable, or a file it can't write) is left as it is and reads back failed; an event the file refuses (full, read only) ends its run failed, its streams still get the `turn.end`, and the chat takes its next message. A run going when its chat is deleted ends `deleted` for the streams open on it. An older `chats.sqlite`, `settings.json`, `runs/` or `work/` directly in the app's home is left untouched and unread, until `reset` of the default file deletes it.
- Each chat has a working folder (`src/deep_reasoning/folders.py`): the worker's cwd, where the agent's Python reads and writes files, so a file from one message is there for the next. It is the folder the user chose (typed, or browsed through `GET /api/folders`; new chats start in settings' default folder while it exists, so a default from another computer gives them their scratch folder), or the chat's scratch folder `work/<chat>/` in the file's data folder, made on its first run and deleted with the chat. A chosen folder is never deleted, and deleting a chat deletes nothing but its own scratch folder. The run's working files (`spec.yaml`, `worker.log`, written tools, the engine's `run_dir`) stay in `runs/<run>/` in the data folder, scratch that a copy of the file doesn't carry. The worker starts with `python -P` and puts the folder last on `sys.path`, so the user's modules import but never shadow an installed one. A run in a folder that is gone is refused before it starts.
- The app gives the agent tools of its own, in `src/deep_reasoning/app_tools.py`, loaded through the engine's `factory_from`, so the engine never changes. Their blocks (`APP_TOOLS` in `library.py`) are added in code, never stored in the file; their names are reserved (a custom tool can't take one, and a shared file's row with one is left out with a warning), and `engine_config()` puts the app file's path, the chat id, the run id, the run's tools folder, the chat's namespace and the providers' key variables in each, and in `library` the namespaces whose chats may write with it (`editors`): in any other chat, or when none are named, its description ends with `READ_ONLY_HERE`, so a librarian sub-agent there reads, and asked for a change says how to make it. Each opens the file as it is (`open_existing`, `mode=ro` or `mode=rw`, with the same trust checks), never making a moved or deleted one afresh. `history` (read-only; a fresh Library grants it only in the `historian` namespace it seeds, with `page`, `spawn: []`, `HISTORIAN_SUFFIX` and worked examples, `*_example.yaml`, each answering in a later cell from what it printed; root holds each one's first two turns under its name, the question and its hand-off, `FinalAnswer(subagent(ctx.task, namespace="historian", history=ctx.history))`, which every namespace inherits but the historian, whose own take their place; the hand-off's thinking, not root's suffix (which the historian inherits), says to pass the message as written; `engine_config()` shows a namespace that can't make a worked example's whole-question hand-off (a last cell `FinalAnswer(subagent(..., namespace=…))` or `switch_namespace(…)` into a namespace its `spawn` list leaves out, itself included, as `check_spawn` decides, or one that is gone) that example with its last turn doing what it can instead: answering itself when it is the target or under it, saying it can't when the target reads the record (`history`), else answering itself if it can (`without_impossible_hand_offs`; a namespace holds an override only where what it inherits differs), leaving what's stored as it is, which the panel lists under the namespace's Hand-offs and a Delete of the target warns of; an older Library isn't changed) returns this chat's earlier runs as plain data, numbered from 1, the chat's first message, through a Python twin of `fold.js`, as `HISTORY_DESCRIPTION` tells the agent; each text in it is cut past `MAX_VALUE_CHARS`, but a page's copies are whole. `library` (granted only in the `librarian` namespace a fresh Library seeds, `tools: [library]`, which nothing inherits, with `spawn: [historian]`, a default the user may widen, not a lock, so it never delegates to itself, `LIBRARIAN_SUFFIX` and worked examples, `read_library_example.yaml`, `worked_example_example.yaml` (writing an example's tags as `[repl]` in a raw string) and `undo_example.yaml`, whose observations a test re-runs; root holds two hand-offs to it, of reading and of changing the Library (`LIBRARIAN_HAND_OFFS`), each named as one of the librarian's own examples so that its own replace them there, and seeded before the historian's hand-offs, as root follows those more reliably nearer the task; root's `ROOT_SUFFIX` says what app its agents are in and names no librarian, so it holds without one; it also carries the guidance on answering numbers from computed variables and fan-outs in words, as a suffix, which measured better per token than a worked example; an older Library isn't changed) reads, from any namespace, the namespaces (`show()` in brief, each text cut past 200 characters; `show(name)` one as the panel shows it), the tools (`tools()`, `tools(name)` whole, a custom tool's source included) and this chat's changes (`changes(turn=None)`, every run's `library.change` events, this one's so far included, a namespace's with the fields it changed and a tool's before and after as `write_tool` takes them, so the agent undoes one by writing its before back); adds or replaces a decomposition (`add_decomposition(..., replace=True)`; each line of an assistant turn that is `[repl]` or `[/repl]` alone written as the real tag (`with_real_tags`: read, rewritten and dumped only when a tag changed; a `[repl]` in code or a user's turn stays) unless the YAML holds a real one, as one read back does; `code_problems` for a turn whose code isn't Python); adds a namespace or changes one's own fields (`add_namespace`, `change_namespace`: its YAML as the panel's Edit YAML shows it, so `system_suffix`, `vars`, `tools` and `spawn`; a change merges (`merged`), each field given in place of its own whole and null taking one out, the merged YAML too held to 1,000,000 characters, unless `replace=True`, which the panel's Edit YAML always does; it returns each field it changed, and logs nothing when none), each with the panel's checks in one transaction, from the worker while the server saves events; and adds or replaces a custom tool (`write_tool(name, source, factory, settings=None)`, which the agent then grants with `change_namespace`): a Python name that is no keyword, built-in's (`llm`, `rag`, `kg`, `safe_url`, `claude_code`), app tool's or name the REPL binds itself (the engine's `RESERVED_NAMES`), settings of plain values (none may be `factory` or `factory_from`), source that parses (`parsed_python`, shared with import and the panel: refused with its line, or as too deep), then built as another chat's run would build it, by `tool_check.check_tools` (shared with import; its docstring is the interface): the engine's `make_tool` inside the run's `LLM.alias` with its client, `models` presets, `llm_kwargs` and `model=`, as `build_reasoner` builds a run's tools, from the run's `spec.yaml` (a run always has one), in the worker's environment, in a process of its own (`python -P`, cwd an empty folder in a folder of its own under the run's `tools/checks/`, deleted after; in a process group ended after, so nothing in that group outlives it (one a tool puts in a session of its own isn't followed); noting each tool's name before building it and its verdict after, in a file named before any tool runs, apart from the tools' own folder, and ending itself whatever happens, its group killed before it is reaped, so a tool that ends or hangs the check, past `BUILD_TIMEOUT_S`, is the one blamed and the rest are checked again), so a tool needing a file or module only the chat's folder has is refused; refused in words with each tool's verdict; and stored as an import stores one (`store_tool`: its block, `factory_from: <name>.py` and its source, kept only if `accepted()`). Only in a chat whose namespace resolves to the `local` REPL, as the build runs the agent's code outside any sandbox; never over a tool root grants (every chat would run the agent's code as one of its own) or one the engine builds from its block alone (`claude_code`, an `llm` preset: no Python to write back). The grant and these locks are checked before the build, and again under the write lock, which the build doesn't hold. Each custom tool `add_namespace` or `change_namespace` grants that no namespace granted yet (one granted elsewhere already builds in every run) is built the same way first, all in one check, after the checks that cost nothing (the name, its place, its vars and spawn, the grant and the locks, the local REPL), so a write refused for them runs no tool; under the write lock the grant, the locks and the local REPL are checked again, and the write is refused if a tool built changed meanwhile. It writes only in a run whose chat's namespace grants `library` through its chain, checked under the same write lock (`allowed`) before anything else, so a sub-agent spawned into `librarian` from a chat in another namespace can't, and a librarian chat's agent may hand the tool to a sub-agent elsewhere (`subagent(..., tools={...})`), in the namespaces its `spawn` allows, by default only historian. It never writes root, its YAML or its decompositions; never sets or changes a namespace's `repl` or `reasoner` (`reasoner: claude_code` would bill Michael's subscription), or adds the app's own tools to a namespace's `tools` or takes them out (granting them is the user's, in the panel); adds no namespace under one whose chain grants `library` or runs Claude Code (its `registry.backbone`, or a tool whose factory is `claude_code`), so no namespace it makes can edit or bill; names no factory of a tool's own as one of the engine's (`check_tool_block`, which every stored block meets, so none reads as `claude_code`), and grants no tool whose factory is `claude_code` that the namespace's stored tools lack (it bills the subscription as `reasoner` would; keeping or removing one is fine), each checked under the same lock against the Library as the engine reads it; has no method for the system prompt, the run settings or deleting; and never writes YAML, a tool's source or its settings as YAML over 1,000,000 characters, or a name, YAML, source or settings holding a provider's key in its text or its parsed data (a tool's string and bytes literals), which an escape can spell (the values of the key variables in the worker's environment, as `secrets_of` finds them), and takes only plain `str`, or for YAML a dict of plain values, which it dumps; nor a text holding the mark of one a brief list cut (`CUT_MARK`). These locks are in `app_tools.py`, as the panel still edits all of it; they guard the tool, not the file, which a cell can open itself. Every refusal, a busy or unwritable file included, is a `LibraryError` in plain words. Each change is logged as `library.change` (what: `decomposition`, `namespace` or `tool`; namespace, none for a tool; name, which for a namespace is its own; before, None when added; after, as stored: a tool's row, its block's YAML, then `# <name>.py` and its source, `tool_text`, so a settings or factory change shows and writing the before back restores it), which the worker records as a run event of the calling agent's node and its open cell; a Stop never falls between a write and its log (`stop_proof`). The page shows each as a step in the tree and as a line under the answer, worded by `changeText` in `fold.js` ("added namespace research", "replaced tool word_count"), each opening onto its before and after YAML or source, as untrusted text only (any cell can log one, and a shared file can hold any), and on a live run's change the Library panel reads the Library afresh, keeping its drafts, and so does the namespace menu under the message box; `history.steps` lists it too. A change applies from the next message, and undoing one is asking the agent to write the before back, which it reads with `changes()`. The design is the sub-page under the Notion page's Notes. `page` (granted in the `historian` namespace a fresh Library seeds) shows the user a page the app draws from plain data, never HTML: `step(turn, node=None, index=…)` and `agent(turn, node)` copy `history.steps(turn, node)[index]` and a sub-agent's drives through `History`, as fold.js folds them, beside `text` and `table`; keys are withheld, the limits in `pages.py` refused in words, and `open()` saves only what reads back exactly, in the `pages` table, and logs `page.open`, which the chat links, as a step and a line under the answer, to `/pages/<id>`, drawn by `page.js` with the chat's renderers (`tree.js`); opened again, it saves in place, logging nothing.
- No sandboxing or safety layers, and nothing from the old app's OpenHands or ACP stack.

## Checks

- `uv sync`, then `uv run deep-reasoning` serves the app at http://127.0.0.1:8000 and opens a tab (`--port` to change the port, `--no-browser` to skip the tab). `uv run deep-reasoning import CONFIG.yaml` reads an engine config into the Library. Serving, `import` and `reset` each take `fcntl.flock` on `<the file's real path>.lock` (a file of its own, as SQLite's locks are on the Library's) before they open the file (`owning`), refuse while another holds it, and never delete it (an import that made the Library and wrote nothing deletes that, `forget`); where flock isn't supported they warn and go on. A `--library` in a missing folder is refused. `uv run deep-reasoning reset` deletes the app file's side files, then the file, its data folder and, for the default file only, an older version's leftovers in the app's home, after listing them and asking (`--yes` doesn't ask). It refuses, deleting nothing, a path naming no file, a symlink (naming its target), a folder or anything else but a file, and a file it can't read through `open_existing(..., "ro")` as a version 1–4 Library, so nothing writes the file before the user types `delete`; it keeps `.env`, every folder a chat or the settings chose, and a folder holding one. The UI is static files in `src/deep_reasoning/web/`, no build step, served at `/`; marked, DOMPurify and js-yaml are cdnjs's pinned files copied into `web/vendor/`, so the page loads nothing from elsewhere.
- `uv run pytest` (no network: the model is a fake on 127.0.0.1); `node --test tests/*.test.mjs` (the fold, the tree, the model menu and the turn check, no dependencies); `uv run ruff check && uv run ruff format --check`; `node --input-type=module --check < FILE` for each of `src/deep_reasoning/web/app.js`, `fold.js`, `tree.js`, `models.js`, `page.js`, `library.js`, `settings.js` and `turns.js` (as modules: a plain `node --check app.js` misses errors such as a name declared twice, which stop the page loading).
- `uv run pytest -m live -s` runs the gpt-6-luna live test, a paid call, and logs what it spent; it needs `OPENAI_API_KEY` (in a cloud session `OPENAI_API_KEY=placeholder`: the network proxy adds the real one).
- Check each UI change in a real browser against `uv run deep-reasoning --no-browser` (Playwright is preinstalled in cloud sessions): a new chat, a live run with its tree opened, a follow-up, a reload mid-run, Stop, rename, delete, a restart, both themes, phone width, no console errors.
- To drive the UI without a paid model: serve `tests/fake_model.py`'s `FakeOpenAI` from a process of its own on a scripted plan (`scripts/record_runs.py` has fan-outs, nested delegation and a run to stop), run `HOME=<tmp> uv run deep-reasoning --no-browser --library <tmp>/lib.sqlite`, add the fake in settings as a custom server (its `base_url`, any key), and pick one of its models under the input (`library_on` in `tests/conftest.py` does the same through `settings.py`). `HOME` keeps its keys, runs and scratch folders out of your own `~/.deep-reasoning`.
- The fold's fixtures in `tests/runs/` are real runs against the fake model, recorded from the app file, never typed: `uv run python scripts/record_runs.py`. Record them again when the worker's events change.
